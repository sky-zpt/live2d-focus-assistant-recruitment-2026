# Python Issue 设计文档

## 1. 使用背景

本项目是数学建模协会技术组的招新面试基座。它是一个 Live2D 专注助手：用户输入任务、开始一段专注时间、完成后保存记录并由角色反馈。

本文件用于在完整版本验收后创建 GitHub Issue。考生可按兴趣与能力认领一个或多个 Issue，也允许多人认领同一个 Issue；Issue 之间不能存在必须的先后顺序，也不能要求考生先等待其他 Issue 合并。

Live2D 只负责视觉和声音反馈。本批 Issue **只针对 Python 部分**，不要求修改 HTML、CSS、JavaScript、模型资源或动作文件。

## 2. 对 Issue 作者的统一要求

每个 Issue 创建时必须包含：

- 背景：当前代码或用户流程有什么不足；
- 目标：考生最终要增加或修复什么行为；
- 修改范围：建议涉及的 Python 模块；
- 验收标准：可以通过接口调用、命令行操作或检查数据库结果验证；
- 不在范围内：明确禁止扩大成登录、AI、云同步等功能。

测试由维护者统一提供，不将“补测试”“写配置”“补 README”单独发布为考生 Issue。考生仍需在 PR 中说明自己的验证过程，但这不是 Issue 的主要交付物。

## 3. 难度定义

### Easy

概念较单一，通常修改一个服务函数或一个独立的 Python 模块，但必须包含完整输入、处理、输出和边界行为，不能是几行计算器代码。

### Moderate

需要理解现有服务层、API 数据结构或多步数据处理流程，通常会涉及两个以上函数，但不要求修改数据库结构或处理复杂事务。

### Hard

需要理解多个模块、时间/数据一致性或较复杂算法。Hard 不等于“数据库专家题”：本批只有 2 个 Issue 直接修改数据库，其余 Hard 分别考察算法、状态恢复和批处理设计。

## 4. 难度分布

| 难度 | 数量 | 主要范围 |
| --- | ---: | --- |
| Hard | 5 | 2 个数据库、3 个业务算法/状态处理 |
| Moderate | 6 | 服务层、统计、CLI、接口行为 |
| Easy | 9 | 输入处理、记录展示、轻量数据分析 |

## 5. Hard Issue（5 个）

### H01：历史记录安全分页与多条件查询

**背景**：当前历史接口只有简单 `limit`，用户无法按日期、状态和时长查看记录。

**目标**：在 Python 仓储层和 API 中增加分页及多条件查询。

**要求**：

- 支持页码、每页数量、状态、开始日期、结束日期和最短时长；
- 返回记录列表、总记录数、当前页和总页数；
- 排序字段只能使用明确白名单；
- 所有值和条件使用参数化 SQL；
- 保持不传筛选条件时的默认查询行为。

**验收**：使用不同状态、日期和页码请求接口，返回数量、顺序和分页元数据正确；非法参数能得到明确错误。

**考察**：SQL 查询构造、分页、参数校验。

### H02：专注记录 JSON 导入导出

**背景**：用户无法迁移或备份自己的专注记录。

**目标**：实现 Python 服务，将记录导出为带版本号的 JSON，并导入到当前数据库。

**要求**：

- 导出包含格式版本和记录列表；
- 导入前检查字段、状态、时间和数值范围；
- 重复记录不能重复插入；
- 导入中途出现错误时，已有数据不能被部分修改；
- 不允许导入活动状态记录造成开放会话冲突。

**验收**：导出后清空或换用数据库，再导入并核对记录；导入非法文件时数据库内容保持不变。

**考察**：JSON、事务、数据完整性。

### H03：连续专注天数与最长记录算法

**背景**：当前产品只能展示历史记录，无法反馈连续完成带来的成就感。

**目标**：实现独立的连续日期分析服务，返回当前连续天数、历史最长连续天数和最近完成日期。

**要求**：

- 同一天完成多次只算一天；
- 以本地时区日期计算；
- 正确处理跨月、跨年和中断日期；
- 没有完成记录时返回 0 和空日期；
- 不把算法写入 Flask 路由。

**验收**：用包含重复日期、跨月和断档的记录调用服务，结果符合预期。

**考察**：日期算法、集合、排序和边界处理。

### H04：异常中断会话的自动结算

**背景**：浏览器关闭或程序异常退出后，数据库可能长期保留 `active` 会话。

**目标**：实现服务识别并处理超时未更新的活动会话。

**要求**：

- 根据最后开始时间和可定义的超时窗口识别异常会话；
- 将异常会话转为 `abandoned`，保留原任务和已消耗时间；
- 不修改 `completed`、`paused` 等其他状态；
- 同一会话重复清理不会产生额外变化；
- 清理逻辑可以被 API 或 CLI 调用。

**验收**：准备多个不同状态和时间的会话，执行清理后只有符合条件的活动会话被处理。

**考察**：状态机、时间比较、幂等操作。

### H05：批量专注报告生成

**背景**：用户只能看到单条记录，无法获得一段时间的整体反馈。

**目标**：实现一个 Python 报告服务，根据给定日期范围生成结构化报告。

**要求**：

- 输出完成次数、放弃次数、累计时长、平均时长、完成率和最长连续天数；
- 报告必须由真实记录计算，不允许写死数字；
- 日期范围为空时使用合理默认范围；
- 空数据也能生成完整的零值报告；
- 报告结果同时提供结构化字典和可读文本两种形式。

**验收**：分别使用空数据、单条记录和混合状态记录生成报告，所有字段和文本一致。

**考察**：多步骤数据处理、服务组合、结果建模。

## 6. Moderate Issue（6 个）

### M01：每日专注汇总

实现按日期分组的完成次数、放弃次数和专注分钟数。

验收：跨天记录分组正确，日期顺序稳定，空数据返回空列表。

考察：字典分组、日期处理、排序。

### M02：时间段专注分析

将记录按上午、下午、晚上分组统计。

验收：时间段边界明确；每条记录只归入一个分组；空数据返回零值。

考察：条件分支、时间解析、聚合。

### M03：历史关键词搜索

为历史记录增加任务关键词搜索，支持不区分大小写的英文搜索和精确的中文子串搜索。

验收：首尾空格、空关键词、无匹配和特殊字符均有明确行为；用户输入不能被当作 SQL 片段执行。

考察：字符串处理、查询参数、安全意识。

### M04：命令行历史浏览器

增加 `python -m src.cli history`，支持数量、状态和关键词参数。

验收：命令行能展示任务、状态、时长和时间；参数错误有可读提示；不依赖浏览器页面。

考察：CLI 参数、服务复用、格式化输出。

### M05：专注完成率趋势

计算最近若干个自然周期的完成率，例如按周输出完成次数、结束次数和完成率。

验收：周期边界稳定；分母为零时结果为零；结果按时间顺序返回。

考察：日期区间、聚合、数值处理。

### M06：记录摘要与报告文本模板

将会话记录和统计结果转换为统一的中文摘要，供 API 和 CLI 复用。

验收：完成、放弃、暂停和进行中记录显示不同状态；缺少可选时间字段时不会崩溃；不直接暴露数据库 Row。

考察：数据转换、模板设计、空值处理。

## 7. Easy Issue（9 个）

### E01：任务文本规范化

统一处理首尾空格、连续空格和换行，同时保留中文内容。

验收：空文本拒绝，普通文本规范化结果稳定。

### E02：自定义时长输入校验

将专注时长校验集中为一个可复用 Python 函数，限制为 1–120 分钟并拒绝布尔值、小数和负数。

验收：合法整数通过，所有非法类型和边界有明确错误。

### E03：秒数中文格式化

将秒数转换为“30 秒”“5 分钟”“1 小时 5 分钟”等中文文本。

验收：0、59、60、3600 和较大值结果正确，负数被拒绝。

### E04：完成率计算函数

根据完成数和结束总数计算百分比。

验收：分母为零返回 0；分子大于分母时有明确处理；结果精度统一。

### E05：记录状态中文映射

将内部状态映射为“进行中、已暂停、已完成、已放弃”。

验收：所有已知状态正确，未知状态不能静默显示为空。

### E06：时长区间分类

将记录按少于 10 分钟、10–30 分钟、超过 30 分钟分类。

验收：10 和 30 分钟边界归类明确，空列表和零时长行为明确。

### E07：安全生成单条记录摘要

将一条会话记录转换为一行可读文本，处理缺失时间和异常状态。

验收：任务文本包含特殊字符时仍作为普通文本处理；所有状态都有输出。

### E08：查询参数解析

统一解析 `limit`、页码和日期字符串，返回规范化 Python 值。

验收：缺省值、非法类型、越界值和日期格式错误均有明确结果。

### E09：专注时段分类统计

根据开始时间统计上午、下午和晚上各有多少条记录。

验收：边界时间归类稳定，空数据返回完整的零值字典。

## 8. 随机认领与合并规则

### 认领规则

- 每个考生可以认领一个或多个 Issue；
- 认领时须在原 Issue 下评论 `姓名：真实姓名，已认领`；
- 允许多个考生同时认领同一个 Issue，并分别提交自己的实现；
- 项目贡献截止日期为 2026 年 9 月 27 日，具体关闭时间以招新通知为准；
- Issue 不设置“必须先完成”的前置任务；
- Issue 描述中提供足够的现有接口和数据结构背景；
- 考生不需要修改前端，不需要等待其他考生的代码。

### 维护者准备工作

- 在基座中预留 `analytics.py`、`import_export.py`、`cli.py` 等模块入口；
- 为每个 Issue 准备独立的验收数据和隐藏检查；
- 对涉及同一文件的 Issue，提前拆出独立函数或通过分支合并解决冲突；
- 不把 Issue 设计成“补测试”“改配置”“写文档”这类工程杂务。

### 统一完成标准

考生的 PR 仍需遵守项目总的 PR 描述规范，说明改动、验证方式、遇到的问题和参考资料；但这些内容属于 PR 交付规范，不改变 Issue 的 Python 功能目标。
